# Frontend Slides

创建零依赖、动画丰富的 HTML 演示文稿，完全在浏览器中运行。

## 核心原则

1. **零依赖** — 单个 HTML 文件，内联 CSS/JS。无需 npm，无需构建工具。
2. **展示而非讲述** — 生成视觉预览，而非抽象选择。人们通过看到实物来发现自己想要什么。
3. **独特设计** — 不要千篇一律的"AI 模板味"。每个演示文稿都必须有定制感。
4. **渐进披露** — 先读取轻量的样式索引。对于大胆模板，使用小型预览卡展示样式预览，仅当用户选定某模板后才加载其完整的 `design.md`。
5. **固定 16:9 舞台（不可商量）** — 每个演示文稿使用 1920×1080 幻灯片画布，整体缩放至视口。幻灯片必须在每块屏幕上保持 16:9，包括手机。不要重新回流幻灯片内容以适配设备。

## 设计美学

你倾向于向通用、"主流分布"的输出靠拢。在前端设计中，这会产生用户所说的"AI 模板味"。避免这种情况：做有创意、有辨识度的前端，令人惊喜、愉悦。

重点关注：

- **字体排印**：选择美观、独特、有趣的字体。避免 Arial、Inter 等通用字体；选择能提升前端美感的独特字体。
- **色彩与主题**：坚持统一的美学。使用 CSS 变量保持一致性。主色搭配锐利点缀色优于怯懦、均匀分布的调色板。可从 IDE 主题和文化美学中汲取灵感。
- **动效**：用动画做效果和微交互。HTML 优先用纯 CSS 方案；React 可用时使用 Motion 库。聚焦高影响力时刻：一次精心编排的页面加载配合错落显现（animation-delay），比零散的微交互更令人愉悦。
- **背景**：营造氛围与深度，而非默认纯色。叠加 CSS 渐变、几何图案，或与整体美学匹配的情境效果。

避免通用的 AI 生成美学：

- 被滥用的字体族（Inter、Roboto、Arial、系统字体）
- 老套的配色方案（尤其是白底紫渐变）
- 可预测的布局和组件模式
- 缺乏情境个性的千篇一律设计

创造性地解读，做出意外但贴合情境的选择。在浅色与深色主题、不同字体、不同美学间变换。你仍倾向于在多次生成中收敛到常见选择（例如 Space Grotesk）。避免这一点：跳出框架思考至关重要！

## 固定舞台规则

以下不变式适用于每个演示文稿中的**每一张**幻灯片：

- 每个演示文稿有一个填满浏览器窗口的视口包裹层。
- 每张幻灯片在固定的 1920×1080 舞台内编写。
- 舞台整体缩放以适配视口。可以留黑边；不得重新布局内容。
- 不要用响应式断点为手机重排幻灯片内容。
- 在 1920×1080 设计尺寸下使用固定的内部幻灯片度量。
- 幻灯片可见性必须由 `.active` / `.visible` 通过 `viewport-base.css` 中的 `visibility`、`opacity` 和 `pointer-events` 控制。不要用 `display: none` / `display: block` 切换幻灯片；后继布局类如 `.slide-content { display: flex; }` 会覆盖它们，导致所有幻灯片同时可见。
- `clamp()` 仅用于舞台外的非幻灯片 UI，或全舞台不实际的小型回退预览。
- 包含 `prefers-reduced-motion` 支持
- 不要直接取反 CSS 函数（`-clamp()`、`-min()`、`-max()` 会被静默忽略）— 改用 `calc(-1 * clamp(...))`

**生成时，读取 `viewport-base.css` 并将其完整内容包含在每个演示文稿中。**

### 内容密度模式

询问用户这主要是一个阅读型演示还是演讲型演示，然后据此设计：

| 密度模式 | 适用场景 | 设计行为 |
| -------- | -------- | -------- |
| **低密度 / 演讲主导** | 公开演讲、Keynote 风格分享、现场讲解 | 每张幻灯片一个观点、大号字体、强视觉层级、充足留白、最多 1-3 个要点，需要时增加幻灯片数 |
| **高密度 / 阅读优先** | 报告、讲义、异步评审、详细内部文档 | 更自成体系、结构化网格/表格/注释、4-8 个要点或 4-6 张卡片（在可读前提下）、更紧凑但仍有意的间距 |

基线限制依然适用：不滚动、不溢出、不重叠面板、文字不低于舒适阅读尺寸。若内容超出所选密度模式，拆成更多幻灯片，不要压缩到拥挤。

## 阶段 0：检测模式

判断用户想要什么：

- **模式 A：新建演示** — 从零创建。进入阶段 1。
- **模式 B：PPT 转换** — 转换 .pptx 文件。进入阶段 4。
- **模式 C：增强** — 改进已有 HTML 演示。先读、理解、再增强。**遵循下方模式 C 的修改规则。**

### 模式 C：修改规则

增强已有演示时，固定舞台适配是最大风险：

1. **添加内容前：** 清点已有元素，对照密度限制检查
2. **添加图片：** 让其容纳在 1920×1080 幻灯片画布内。若幻灯片已满，拆成两张
3. **添加文字：** 每张最多 4-6 个要点。超限？拆成续接幻灯片
4. **任何修改后，验证：** 幻灯片舞台保持 16:9、无文字溢出卡片、无面板重叠，且在 1280×720 加一个手机视口的截图都正确
5. **主动重组：** 若修改会导致溢出，自动拆分内容并告知用户。不要等被问

**向已有幻灯片添加图片时：** 将图片移至新幻灯片，或先减少其他内容。绝不未检查 1920×1080 舞台是否已满就添加图片。

## 阶段 1：内容发现（新建演示）

**一次性问完所有问题**，让用户一次填完。若当前环境提供原生结构化提问 UI，使用它；否则用一条带清晰编号选项的简洁消息提问：

**问题 1 — 用途**（标题："用途"）：
这份演示用于什么？选项：路演 Pitch / 教学教程 / 会议演讲 / 内部汇报

**问题 2 — 篇幅**（标题："篇幅"）：
大约多少张幻灯片？选项：短篇 5-10 / 中篇 10-20 / 长篇 20+

**问题 3 — 内容**（标题："内容"）：
内容准备好了吗？选项：内容齐备 / 粗略笔记 / 仅主题

**问题 4 — 密度**（标题："密度"）：
演示密度感如何？选项：

- "低密度 / 演讲主导" — 大观点、少文字、更多视觉呼吸空间
- "高密度 / 阅读优先" — 更多自成体系的细节，便于异步阅读

**阶段 1 不要询问内联编辑。** 用户不应在看到草稿前就选择编辑行为。内联编辑是草稿后的能力：默认包含，除非用户明确要求锁定/仅导出文件。

记住用户的密度选择。它影响幻灯片数、字号、每页文字量、布局密度，以及偏向电影感演讲幻灯片还是自成体系的阅读幻灯片。

若用户已有内容，请其分享。

### 步骤 1.2：图片评估（若提供图片）

若用户选了"无图片" → 跳至阶段 2。

若用户提供图片文件夹：

1. **扫描** — 列出所有图片文件（.png、.jpg、.svg、.webp 等）
2. **逐张检查** — 用 agent 可用的图像理解能力。若无法读图，用文件名/元数据，仅在需要时请用户澄清
3. **评估** — 每张：展示什么、可用/不可用（附原因）、代表什么概念、主色调
4. **共设计大纲** — 精选图片与文字共同决定幻灯片结构。这不是"先规划幻灯片再贴图"— 从一开始就围绕两者设计（例如 3 张截图 → 3 张功能页，1 个 logo → 标题/结尾页）
5. **确认大纲** — 在可用时用同样的结构化提问机制："这个幻灯片大纲和图片选择看起来对吗？"选项：可以 / 调整图片 / 调整大纲

**预览中的 Logo：** 若识别到可用 logo，在阶段 2 的每个样式预览中（base64）内嵌它 — 用户看到自家品牌以三种风格呈现。

## 阶段 2：风格发现

**这是"展示而非讲述"阶段。** 多数人无法用语言表达设计偏好。

### 步骤 2.0：直接生成 3 个风格预览

基于用途、受众、情绪和内容密度，生成 3 个差异明显的单页 HTML 预览，展示字体、色彩、动画和整体美学。

不要问用户是否想要选项或预设选择器。默认发现体验始终是视觉对比。

若用户已给出氛围，用它。若没有，从场合、受众、内容、利害推断可能情绪。让选项足够多样，使用户能视觉反应，而非必须先表达品味。

若用户明确点名某个预设或大胆模板，将其作为一个选项，其余预览位围绕它生成。

阅读 [STYLE_PRESETS.md](STYLE_PRESETS.md) 了解安全预设候选。若 [bold-template-pack/selection-index.json](bold-template-pack/selection-index.json) 存在，也读取该精简索引，但暂不读任何 `design.md` 文件。

| 情绪                | 建议预设                                          |
| ------------------- | ------------------------------------------------ |
| 钦佩/自信 | Bold Signal、Electric Studio、Dark Botanical     |
| 激动/振奋    | Creative Voltage、Neon Cyber、Split Pastel       |
| 平静/专注        | Notebook Tabs、Paper & Ink、Swiss Modern         |
| 受启发/感动    | Dark Botanical、Vintage Editorial、Pastel Geometry |

**预览组合规则：**

- 默认生成 3 个预览：1 个来自 `STYLE_PRESETS.md` 的安全预设、至少 1 个来自 `bold-template-pack/selection-index.json` 的大胆模板、1 个通配。
- 通配可以是第二个大胆模板，或自创设计。选择能为用户场合、受众、情绪、内容制造最强、最有用对比的那一种。
- 不要强求所有表现型选项都来自模板库。若简报比现有模板更锐利、更具体，用通配位自由设计。
- 对保守或高风险演示，让安全预设特别克制；选一个沉稳、正式度较高的大胆模板；让通配是另一个克制模板或一个权威而非装饰感的自定义设计。
- 对表现型演示，安全预设作为可读回退；选一个强力大胆模板；让通配冒险、贴合情境、与其余两个预览明显不同。
- 若大胆模板匹配感弱，用通配做自定义设计或回退到另一个安全预设，而非强塞模板。

**自定义通配设计规则：**

- 遵循上方设计美学章节：无通用"AI 模板味"、无默认字体/配色/布局、无白底紫渐变老套、无千篇一律的仪表盘/卡片观感。
- 匹配用户所述场合、受众、情绪/氛围和内容密度。自定义设计应有为这份演示量身定制之感，而非仅仅"时髦"。
- 做出明确视觉立论：独特字体、坚定的调色板、可辨识的布局系统、一个强烈的氛围或图形装置。
- 让它对完整演示可行。预览须暗示一个可扩展到章节页、内容页、引用页、对比页、结尾页的设计系统。
- 遵循固定 1920×1080 舞台规则，通过与其他选项相同的预览真实性检查。
- 绝不在幻灯片上渲染"custom"、"wildcard"、"AI-generated"或设计过程标签。

**大胆模板选择规则：**

- 将用户用途和情绪与 `mood`、`tone`、`best_for`、`avoid_for`、`formality`、`density`、`scheme` 匹配。
- 把 `best_for` 示例当作软信号，非严格行业过滤。
- 让三个预览彼此真正不同。
- 选定大胆模板候选后，仅读取那些候选在索引 `preview_md` 路径下的 `preview.md` 文件。
- `preview.md` 仅用于标题页预览。用户选定最终模板前不要读完整 `design.md`。
- 除非所选最终 `design.md` 缺关键实现细节，否则不要读或复制 `template.html`。

**预览真实性规则（不可商量）：**

- 每个风格预览必须看起来像用户演示的真实首页，而非诊断卡。
- 绝不在幻灯片上渲染内部工作流文字：无 `preview`、`generated from`、`preview.md`、`template`、`preset`、`style option`、`Option A/B/C`、文件名、路径或来源文档标签。
- 绝不在幻灯片本身渲染模板名或 slug 名。模板/样式名只出现在给用户的消息中。
- 绝不把用户需求备注渲染为幻灯片内容，如"锐利挑衅"、"安全选项"、"大胆选项"、"用于内部分享"或"受众：..."，除非用户明确要求该短语出现在演示中。
- 若幻灯片需要装饰元素，只用真实演示装饰：演示标题、章节标题、日期、作者、公司、页码，或来自用户材料的真实内容短语。
- 打开预览前，检查可见文字，若有内部元数据出现则修订。

将预览保存到 `.frontend-slides/slide-previews/`（style-a.html、style-b.html、style-c.html）。每个应自成体系、精简，展示一张带动画的标题页。

为用户自动打开每个预览。

### 步骤 2.1：用户选择

询问（标题："风格"）：
你偏好哪个风格预览？选项：风格 A: [名称] / 风格 B: [名称] / 风格 C: [名称] / 混搭元素

若"混搭元素"，询问具体细节。

## 阶段 3：生成演示

用阶段 1 的内容（文字，或文字+精选图片）和阶段 2 的风格生成完整演示。

若提供了图片，幻灯片大纲在步骤 1.2 已纳入它们。若没有，CSS 生成的视觉（渐变、形状、图案）提供视觉趣味 — 这是一条完全支持的一等路径。

在整个演示中应用用户的密度选择：

- **低密度 / 演讲主导：** 用更多幻灯片、每页更少观点。偏大标题、短句、视觉隐喻、章节节拍、引用/陈述页、适合演讲者的节奏。
- **高密度 / 阅读优先：** 让幻灯片更自成体系。用结构化网格、对比表、带注释图示、图注、精简说明文字。保持强层级，使其有设计感，而非文档贴上幻灯片。

若用户所述需求混合，选择更接近的两种模式之一，而非发明中间项：现场说服受众默认低密度；异步传阅或详细评审默认高密度。

绝不让高密度变成视觉杂乱。若高密度幻灯片开始溢出，拆分或重新设计成更清晰的结构。

若用户从 `bold-template-pack` 选了大胆模板，生成前读取那一个模板的完整 `design.md`。不要读其他大胆模板。把 `design.md` 当作设计配方：

- 保留其字体、调色板、装饰词汇、间距节奏、组件语法。
- 无论源模板原本用 `deck-stage.js` 还是视口流式 CSS，最终演示生成为固定 1920×1080 舞台整体缩放至视口。
- 将 `design.md` 中的视口流式值视为设计比例，转译为 1920×1080 舞台坐标。不要在最终演示中保留为实时视口回流规则。
- 输出保持单个自包含 Frontend Slides HTML 文件。
- 不要复制演示幻灯片内容或过于字面地模仿源模板。
- `template.html` 仅作所选模板的最后兜底实现参考。
- 生成后，在渲染浏览器截图中验证内容溢出和面板重叠。仅靠 `scrollHeight` 检查不够，因为网格面板可能相互视觉覆盖。

若用户选了自创通配，把该预览的 CSS 和布局当作设计配方：

- 保留其字体、调色板、装饰词汇、间距节奏、网格逻辑、组件语法。
- 将同一视觉系统扩展到完整演示。用户选定自定义方向后不要切换到预设或大胆模板。
- 从该系统设计任何缺失的幻灯片布局，而非从其他风格导入图案。
- 输出保持固定舞台、单文件、像其他演示一样经过视觉验证。

**生成前，读取这些支持文件：**

- [html-template.md](html-template.md) — HTML 架构与 JS 特性
- [viewport-base.css](viewport-base.css) — 强制 CSS（完整包含）
- [animation-patterns.md](animation-patterns.md) — 所选感觉的动画参考

**关键要求：**

- 单个自包含 HTML 文件，所有 CSS/JS 内联
- 在 `<style>` 块中包含 viewport-base.css 的完整内容
- 使用 Fontshare 或 Google Fonts 字体 — 绝不用系统字体
- 为每个章节添加详细注释
- 每个章节需有清晰的 `/* === 章节名 === */` 注释块

## 阶段 4：PPT 转换

转换 PowerPoint 文件时：

1. **提取内容** — 运行 `python scripts/extract-pptx.py <input.pptx> <output_dir>`（需要时安装 python-pptx：`pip install python-pptx`）
2. **与用户确认** — 呈现提取的幻灯片标题、内容摘要和图片数量
3. **选择风格** — 进入阶段 2 做风格发现
4. **生成 HTML** — 转为所选风格，保留所有文字、图片（来自 assets/）、幻灯片顺序，以及演讲者备注（作为 HTML 注释）

## 阶段 5：交付

1. **清理** — 删除 `.frontend-slides/slide-previews/`（若存在）
2. **打开** — 用 `open [filename].html` 在浏览器启动
3. **总结** — 告知用户：
   - 文件位置、风格名、幻灯片数
   - 导航：方向键、空格、（如启用）滑动/点击
   - 如何自定义：`:root` CSS 变量改色、字体链接改字体、`.reveal` 类做动画
   - 内联文本编辑可用：悬停左上角或按 E 进入编辑模式、点击任意文字编辑、Ctrl+S 保存
   - 提供草稿后的自然动作：请用户修订、直接在浏览器编辑文字、或导出/分享

## 阶段 6：分享与导出（可选）

交付后，**询问用户：** _"想分享这份演示吗？我可以部署到实时网址（任何设备包括手机都能用）或导出为 PDF。"_

选项：

- **部署到网址** — 可分享链接，任何设备可用
- **导出为 PDF** — 通用文件，适合邮件、Slack、打印
- **两者都要**
- **不用了**

若用户拒绝，到此为止。若选一项或两项，继续下方。

### 6A：部署到实时网址（Vercel）

这会把演示部署到 Vercel — 一个免费托管平台。链接在任何设备（手机、平板、笔记本）上可用，并持续在线直到用户下线。

**若用户从未部署过，逐步引导：**

1. **检查 Vercel CLI 是否安装** — 运行 `npx vercel --version`。若未找到，先安装 Node.js（macOS `brew install node`，或从 https://nodejs.org 下载）。

2. **检查用户是否登录** — 运行 `npx vercel whoami`。
   - 若未登录，解释：_"Vercel 是免费托管服务。部署需要账户。我带你走一遍："_
     - 步骤 1：请用户在浏览器打开 https://vercel.com/signup
     - 步骤 2：可用 GitHub、Google、邮箱注册 — 哪个方便用哪个
     - 步骤 3：注册后，运行 `vercel login` 并按提示操作（会打开浏览器授权）
     - 步骤 4：用 `vercel whoami` 确认登录
   - 等用户确认已登录后再继续。

3. **部署** — 运行部署脚本：

   ```bash
   bash scripts/deploy.sh <path-to-presentation>
   ```

   脚本接受文件夹（含 index.html）或单个 HTML 文件。

4. **分享网址** — 告知用户：
   - 实时网址（来自脚本输出）
   - 它在任何设备上都可用 — 可发短信、Slack、邮件
   - 以后下线：访问 https://vercel.com/dashboard 删除项目
   - Vercel 免费额度很充裕 — 不会收费

**⚠ 部署注意点：**

- **本地图片/视频必须随 HTML 一起上传。** 部署脚本自动检测 HTML 中通过 `src="..."` 引用的文件并打包。但若演示通过 CSS `background-image` 或不寻常路径引用文件，可能遗漏。**部署前验证：** 打开部署网址，检查所有图片是否加载。若有损坏，最稳妥的修复是把 HTML 和所有资源放入同一文件夹，部署整个文件夹而非单个 HTML 文件。
- **演示含大量资源时优先部署文件夹。** 若演示位于一个文件夹中，图片在旁（如 `my-deck/index.html` + `my-deck/logo.png`），直接部署文件夹：`bash scripts/deploy.sh ./my-deck/`。这比部署单个 HTML 文件更可靠，因为整个文件夹内容原样上传。
- **带空格的文件名能用但可能出问题。** 脚本处理文件名空格，但 Vercel 网址把空格编码为 `%20`。可能的话，避免图片文件名含空格。若用户图片有空格，脚本能处理 — 但若图片仍损坏，把文件名中的空格改为连字符即可。
- **重新部署更新同一网址。** 对同一演示再次运行部署脚本会覆盖之前的部署。网址保持不变 — 无需分享新链接。

### 6B：导出为 PDF

这会把每张幻灯片截图并合并成 PDF。适合邮件附件、嵌入文档或打印。

**注意：** 动画和交互不保留 — PDF 是静态快照。这正常且预期；向用户提及以免意外。

1. **运行导出脚本：**

   ```bash
   bash scripts/export-pdf.sh <path-to-html> [output.pdf]
   ```

   若未给出输出路径，PDF 保存在 HTML 文件旁。

2. **背后发生了什么**（向用户简要解释）：
   - 无头浏览器以 1920×1080（标准宽屏）打开演示
   - 逐张截屏
   - 所有截图合并为单个 PDF
   - 脚本需要 Playwright（浏览器自动化工具）— 缺失时自动安装

3. **若 Playwright 安装失败：**
   - 最常见问题是 Chromium 未下载。运行：`npx playwright install chromium`
   - 若仍失败，可能是网络/防火墙问题。请用户换网络试。

4. **交付 PDF** — 脚本自动打开它。告知用户：
   - 文件位置和大小
   - 它到处可用 — 邮件、Slack、Notion、Google Docs、打印
   - 动画被其最终视觉状态替代（仍很好看，只是静态）

**⚠ PDF 导出注意点：**

- **首次运行较慢。** 脚本安装 Playwright 并下载 Chromium 浏览器（约 150MB）到临时目录。每次运行发生一次。提醒用户首次可能要 30-60 秒 — 同一会话内的后续导出更快。
- **幻灯片必须用 `class="slide"`。** 导出脚本通过查询 `.slide` 元素查找幻灯片。若演示用其他类名，脚本会报"找到 0 张幻灯片"并失败。本技能生成的所有演示都用 `.slide`，所以仅对外部创建的 HTML 才需关心。
- **本地图片必须可通过 HTTP 加载。** 脚本启动本地服务器并通过它加载 HTML（这样 Google Fonts 和相对图片路径才工作）。若图片用绝对文件系统路径（如 `src="/Users/name/photo.png"`）而非相对路径（如 `src="photo.png"`），无法加载。生成的演示总用相对路径，但转换或用户提供的可能不是 — 需要时检查并修复。
- **本地图片只要在 HTML 同目录（或相对目录）就会出现在 PDF 中。** 导出脚本通过 HTTP 提供 HTML 父目录，所以像 `src="photo.png"` 的相对路径正确解析 — 包括带空格的文件名。若图片仍不出现，检查：(1) 图片文件确实在引用路径存在，(2) 路径是相对的，而非像 `/Users/name/photo.png` 的绝对路径。
- **大型演示产生大 PDF。** 每张幻灯片截为完整 1920×1080 PNG。18 页演示可能产生约 20MB PDF。若 PDF 超过 10MB，询问用户：_"PDF 为 [大小]。要我压缩吗？会稍微没那么清晰，但文件小很多。"_ 若是，用 `--compact` 标志重新导出：
  ```bash
  bash scripts/export-pdf.sh <path-to-html> [output.pdf] --compact
  ```
  这以 1280×720 而非 1920×1080 渲染，通常减小 50-70% 文件大小，视觉差异极小。
